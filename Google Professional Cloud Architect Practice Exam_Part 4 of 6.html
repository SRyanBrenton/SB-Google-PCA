QuestionQ301

Verified/Designing for security and compliance

You manage your company’s Google Cloud environment. Multiple departments require access to their own projects, and all members within a department will have the same project responsibilities. You want to organize the Google Cloud environment to minimize maintenance and maximize visibility of IAM permissions as each department’s projects are created and retired. You want to follow Google-recommended practices. What should you do?

Explanation

Google Cloud recommends using groups when multiple principals need the same access, instead of assigning roles to individual users. Roles granted at a folder are inherited by projects under that folder; therefore, a department group with IAM roles assigned at its department folder receives consistent access across that department’s projects while membership and permissions are managed centrally.

QuestionQ302

Verified/Designing for security and compliance

To strengthen governance and security, your organization has organized its Google Cloud environment with folders for separate business units. Every business-unit folder contains development, staging, and production subfolders that must meet internal security controls:

  • Production workloads must, by default, be protected from direct internet ingress unless they are explicitly tagged.
  • The application must be reachable by customers over HTTPS.

You need to create a scalable, enforceable model that blocks internet ingress traffic to production folders while selectively permitting direct HTTPS traffic to the required virtual machines. You must also make sure individual project teams cannot override these controls after they are deployed for all existing and future production projects. What should you do?

Explanation

A hierarchical firewall policy associated with each production folder applies to every descendant project and its VPC resources, including projects created later. It can use a higher-priority HTTPS allow rule targeted to the approved VM group, followed by a lower-priority deny rule for other internet ingress. Hierarchical firewall rules inherited from a higher resource level cannot be overridden by lower-level project or VPC firewall rules, providing centrally enforced protection. Secure tags can target the approved VM group in hierarchical firewall rules.

You must deploy a stateful workload on Google Cloud. The workload can scale horizontally, but every instance must read from and write to the same POSIX filesystem. Under high load, the stateful workload must support up to 100 MB/s of writes. What should you do?

Explanation

Cloud Filestore supplies a shared, POSIX-compliant NFS filesystem that multiple instances can mount concurrently. Its performance can be provisioned to meet the required write throughput. Persistent Disk options are per-instance block storage rather than a shared filesystem, and Cloud Storage FUSE is not POSIX compliant.

QuestionQ311

Verified/Designing for security and compliance

You are deploying a new three-tier application to Compute Engine instances in one Virtual Private Cloud (VPC). The architecture is divided into three subnets: a web-tier subnet, an application-tier subnet, and a database-tier subnet.

  • The web tier must receive traffic only from an external load balancer.
  • The application tier must receive traffic only from the web tier.
  • The database tier must receive traffic only from the application tier.

You need to enforce strict traffic-flow control while following Google-recommended practices. What should you do?

Explanation

VPC firewall rules should follow least privilege: allow only the required protocols, ports, sources, and targets. Tier-specific service accounts (or, less strictly, network tags) enable ingress rules that permit only the upstream tier to reach each downstream tier. Google recommends service-account-based source and target filtering when strict control is needed because service accounts are IAM-controlled identities, whereas network tags can be changed by principals able to edit an instance. A firewall rule cannot mix service-account and network-tag criteria in the same rule, so the rules should consistently use one compatible method—preferably service accounts.

Pub/Sub publisher batching improves throughput and efficiency, but it can add latency to individual messages because they wait for a batch to fill. QuestionQ324

Verified/Ensuring solution and operations excellence

Your company runs an application as a Deployment in a Google Kubernetes Engine (GKE) cluster. During rolling deployments of new application versions, the team has caused outages. The outages are rooted in misconfigured parameters used only in production. You want to add preventive controls to the platform to avoid outages. What should you do?

Explanation

A readiness probe determines whether a container is ready to serve traffic, so a newly rolled-out Pod with an invalid production-only configuration is not treated as ready or used to replace healthy capacity. A liveness probe detects an unhealthy container and causes Kubernetes to restart it. Together, these Pod-specification probes provide preventive rollout health controls; scheduled checks and monitoring alerts detect problems only after they occur, while managed instance group health checks do not govern Deployment Pod readiness.
